Independent technical audit · MTP_TESTING · 31 Aug 2026

VLM-PPO Stack Audit

What the CARLA driving stack in MTP_TESTING actually is, where the documentation and the code disagree, and whether the proposed multimodal VLM direction is the right next move.

Scope 22 Python files, 10,047 lines Method Static read + executed probes Changes made none

Bottom line

There is no vision-language model in this codebase, and there never was one. What exists is a 167 K-parameter multimodal CNN-transformer that takes four camera views and a LiDAR height-map, applies two affine modulations derived from an 8-way command flag, mean-pools everything into 128 numbers, and hands them to a PPO MLP. That is a competent multimodal encoder. It is not a VLM, a VLLM, or a VLA, and calling it one will not survive a viva.

More urgently: the policy is handed lane-centering and heading error straight from the CARLA map API, and the reward is computed from those same three numbers. A five-input MLP can maximise this reward with the cameras unplugged. Every result the current design would produce is, structurally, unable to say anything about perception or language. That has to be fixed before any architecture question matters.

The new direction is worth pursuing — but the first thing to build is not a VLM.

The load-bearing observation

There is no data_collected_town01/, no models/, and no Results_VLM/ on disk. The design documents describe latency tables, driving scores and route-completion targets for a system that, on the evidence of the filesystem, has never been run end to end. 2 · What has already been built

Separating this cleanly matters, because the three bodies of work have very different value going forward.

A · What the old MTP/VAE work established

A working TensorFlow CARLA-PPO loop (main.py, test.py, PIL_simulation.py, VAE/): a 95-dim VAE latent over a semantic-segmentation camera plus 5 nav dims = 100-dim observation, a Keras actor–critic, and a processor-in-the-loop TCP harness with real Raspberry Pi latency traces in Results_04/ and Results_05/.

Its established facts are narrower than the documents suggest. It trained and tested on Town02 only, from a single fixed spawn point (main.py:126), with every red light forced green (main.py:264–265). The "~98% route completion" is one memorised route with a 500 m episode cap. What it genuinely established is the engineering harness: sync-mode CARLA, a PIL socket protocol, and measured Pi-class latency of 113–325 ms for a 52 MB encoder. That harness is worth keeping. The VAE and its numbers are not a baseline you can compare against.

B · What the existing VLM code actually implements

One genuinely good module and a ring of scaffolding around it. MultimodalEdgeEncoder is clean, correct, self-testing, and does what its docstring says at the tensor level: multi-view tokenisation with shared weights, view embeddings, FiLM conditioning, self-attention, projection. The CARLA environment wrapper and PPO implementation are also sound as code.

What is not implemented, despite being named as though it were: any language model, any text encoder, any tokenizer, any cross-modal pretraining, any audio path into the driving loop, any trained scene-context head, any route, any evaluation metric beyond episode reward.

C · What is separate

Aanchal_Spring/ is a real, independently working speech pipeline — wav2vec 2.0 features projected into Qwen2-0.5B, with a correctness audit CSV. It has zero connection to the driving stack. Treat it as a component you may later adopt, not as part of the current system.

3 · Problems and questionable decisions

F-01Ground-truth leakage makes the entire perception stack optionalcritical

Two of the five telemetry dimensions — normalised distance from lane centre and normalised heading error — are computed by querying self.map.get_waypoint(), CARLA's ground-truth road graph. They are concatenated into the observation after the transformer, so they reach the policy untouched by any perception.

The reward is speed_factor(speed) × centering_factor(dist) × angle_factor(angle). All three arguments are telemetry dimensions the policy already receives directly. The reward is therefore a closed-form function of three inputs the agent is handed for free.

Consequence: a policy that ignores all four cameras, the LiDAR, and the language channel — reading only 5 scalars — can maximise this reward. Gradient descent will find that solution, because it is by far the easiest one. Any Town01→Town02 transfer number produced by this setup measures how well a 5-input MLP generalises, not how well the multimodal encoder does. This single issue invalidates the experimental design regardless of what encoder sits upstream.

main_vlm_train.py _get_obs() dist_from_center = veh_loc.distance(current_wp.transform.location) main_vlm_train.py _get_obs() norm_angle = acos(dot(veh_fwd, wp_fwd)) / pi main_vlm_train.py step() reward = speed_factor * centering_factor * angle_factor + 0.3 * speech_reward
F-02The "language" channel is a hash function, not a language encodercritical

SlowCognitivePathway.encode_text checks if key in text or text in key against nine underscore-joined anchor keys. Natural sentences never contain "keep_lane", so nearly all real language falls through to torch.randn(128, generator=manual_seed(sum(ord(c) for c in text))) — a deterministic hash with no semantic structure whatsoever.

I ran it. Two synonyms that COMMAND_VOCAB maps to the same command id are orthogonal; a natural instruction is orthogonal to its own canonical token; and an unrelated phrase is no further away than a related one:

cos("turn left at the intersection", "turn_left") = 0.027 cos("steer_left", "turn_left") = 0.085 # same command id in COMMAND_VOCAB cos("please slow down a little", "banana pancakes") = 0.059

So the system has no open vocabulary, no compositionality, no synonym robustness, and no transfer. The 128 dimensions carry at most log₂(9) bits of real signal. Every claim in the documents about "continuous semantic intent embeddings" and "open-vocabulary language" describes this function.

F-03Three train/inference mismatches silently corrupt the pretrained encodercritical
  • FiLM input type flips. pretrain_encoder.py passes command as a list of strings, which routes through the discrete nn.Embedding lookup. main_vlm_train.py passes a continuous 128-d vector, which bypasses that table entirely. The shared film_gen MLP is trained on one input distribution and deployed on a different one.
  • Scene FiLM is never trained but always applied. Pretraining calls the encoder positionally, so scene_context defaults to None and SceneFiLMConditioning is skipped. At RL time it is supplied — so a randomly-initialised affine modulation is applied to every token of a representation that was pretrained without it.
  • telemetry_proj is never trained at all. Pretraining always passes telemetry=None, and PPO runs the encoder under no_grad. The 5 most informative dimensions in the observation are permanently scrambled by a random 2-layer MLP.
F-04PPO currently trains on a frozen, randomly initialised encoder — silentlycritical

train() loads models/pretrained_vlm_encoder.pth only if os.path.exists(...). That file does not exist. The encoder is then .eval()-ed, run under no_grad, and never added to the optimizer. So today, running --mode train optimises a 495 K-parameter MLP on top of a fixed random projection of the images, and prints no warning. The same silent-skip pattern is in test() and PIL_edge_vlm.py.

F-05The success metric scores a parked car at 100%major

success = not collision and ep_steps >= 200. The stall terminal fires at speed_kmh < 1.0 and step_count > 200 — which produces ep_steps == 201, no collision, and therefore a recorded success. A policy that applies zero throttle forever reports a perfect success rate. There is no route completion, no infraction score, no driving score, and no command-adherence metric anywhere in the repo, despite §12 of the design doc specifying all four.

F-06The baseline comparison is not a comparisonmajor

The design doc tables "Legacy baseline ~98% RC (overfit)" against "Proposed ≥85% RC (zero-shot)". These measure different quantities under different rules:

  • The legacy agent drove one fixed spawn point in Town02 with all red lights forced green and a semantic-segmentation camera.
  • The new agent spawns uniformly at random, has no route at all, and obeys traffic lights only in the sense that nothing rewards or penalises it for them.
  • Route completion is not computed anywhere in the new code, so the "≥85%" target has no measurement backing it.

A fair comparison requires re-running the legacy agent under the new protocol. Until then there is no baseline.

F-07Sensor-rig defects, including a dataset/environment mismatchmajor
  • _setup_sensors finds one cam_bp, sets it to the front camera's 125° FOV, and reuses it for all four cameras — so left/right get 125° instead of the specified 90°. collect_data.py creates four separate blueprints with the correct per-camera FOVs. The pretraining dataset and the RL environment therefore have different camera intrinsics.
  • CARLA delivers BGRA; [:, :, :3] yields BGR, called RGB everywhere. Harmless for a from-scratch CNN; wrong for the ImageNet-normalised MobileNetV3 — and wrong for any pretrained vision backbone you adopt next.
  • LiDAR rotation_frequency is never set. CARLA's default is 10 Hz while the simulation ticks at 20 FPS, so each frame captures roughly half a revolution. The "360° surround BEV" is an alternating half-sweep. Worth confirming against your CARLA version.
  • _spawn_npcs calls set_autopilot(True) without binding the Traffic Manager to synchronous mode — collect_data.py does this correctly. In sync mode this is a known source of stalls.
  • NUMBER_OF_PEDESTRIAN = 10 is defined and documented; no pedestrian is ever spawned.
F-08No route, no goal, no navigation signalmajor

The observation contains nothing about where the vehicle is supposed to go. At an intersection the policy has zero information distinguishing left from right. Language was presumably meant to fill that role, but F-02 means it cannot. This is why "route completion" is unmeasurable and why Town01→Town02 transfer reduces to "does lane-following transfer" — a much weaker claim than the documents make.

F-09Command coverage gaps compound F-02minor

reset() samples uniformly from the 13 keys of COMMAND_VOCAB, but _compute_speech_reward handles only 8 of them. The five aliases (keep_speed, steer_left, steer_right, reduce_speed, accelerate) silently return reward 0 — and they also miss the semantic_anchors table, so they get a random hash embedding. Roughly 5 in 13 episodes therefore run with a meaningless language vector and no language reward.

F-10Nothing is seeded; the torchvision fallback is silentminor

SEED = 42 exists in parameters.py and §16 of the design doc promises deterministic seeding across random, numpy and torch. No script calls any seeding function. Spawn points, NPC selection, weather and command choice are all unseeded.

Separately: if torchvision is absent, SceneContextEncoder silently substitutes a random 4-layer CNN with a different feature dimension for the ImageNet MobileNetV3 — same class name, same output shape, entirely different semantics, one printed warning. It is absent in this checkout.

4 · Your twelve questions, answered directly

What parts of the VLM pipeline are already implemented?
None of it, under any standard definition of VLM.

What is implemented is the multimodal encoder half: multi-view tokenisation, view embeddings, conditioned self-attention, latent projection, and a clean coupling to PPO. There is no text encoder, no tokenizer, no image–text alignment objective, no pretrained multimodal backbone, and no generative or reasoning component. The _parse_command path even accepts a raw integer, which tells you what the conditioning signal really is.

What parts are experimental / prototype code?

Everything downstream of multimodal_encoder.py is prototype in the strict sense that it has never produced an artifact. The dataset directory, the pretrained checkpoint directory and the results directory all do not exist.

Three things are worse than prototype — they are stubs shaped like components: encode_text, the SceneContextEncoder projection head, and telemetry_proj. Each has a plausible name, a plausible signature and a plausible output shape, and each is functionally a random number generator. Five files are dead: main_vlm.py, test_vlm_carla.py, PIL_edge_vlm.py, convert.py, tf_multimodal_encoder.py.

What assumptions are currently being made?

The load-bearing ones, most questionable first:

  • That privileged lane geometry in the observation is acceptable because "it's just telemetry". It is not — it is the answer to the task.
  • That a hand-written anchor table is a reasonable stand-in for a language encoder until a real one arrives. It is not, because it produces the appearance of a working language channel.
  • That 160×80 imagery is sufficient. It is well below what any pretrained vision backbone expects, and the mosaic path upsamples 4 views into a single 224×224 frame — roughly 112×56 of real content per view.
  • That a max-height BEV grid is "3D metric awareness".
  • That perspective RGB and top-down BEV can be fused by concatenating tokens with a learned view id, with no geometric correspondence between them.
  • That PPO from scratch in single-environment CARLA at 20 FPS is a tractable training method for a perception-heavy policy.
  • That lane-following without a route constitutes "driving", so that Town01→Town02 transfer is a meaningful generalisation claim.
  • That an if os.path.exists guard around a required checkpoint is a safe default rather than a silent failure.
Is the multimodal fusion strategy technically sensible?
Half of it is good. The other half throws away everything the good half computed.

Sound: sharing one tokeniser across the four RGB views is genuinely parameter-efficient and correct — the views share image statistics. Learned view embeddings are the right way to keep them distinguishable. Joint self-attention across all views lets the model relate what the left camera sees to what the front camera sees, which is exactly what you want.

Unsound: after two transformer blocks compute a rich 1000-token spatial representation, trans_out.mean(dim=1) collapses it to one 64-dimensional vector. Every spatial relationship the attention just computed is averaged away. The model cannot represent "an obstacle on the left at 12 m" — only a global scene average. This is the single biggest architectural flaw after the leakage: you are paying transformer cost and discarding transformer benefit.

Also unsound: sharing the tokeniser idea across RGB and BEV. These are different coordinate frames with different statistics. TransFuser deliberately uses two backbones and attends between them at multiple scales precisely because a single tokeniser cannot serve both. And telemetry bypasses fusion entirely, so the model can never learn "at this speed, that obstacle matters".

Is the camera / LiDAR representation appropriate?
The cameras are too small, and the LiDAR representation is losing most of its information.

Cameras. 160×80 is inherited from the 2022 VAE baseline and was chosen for a Conv-VAE, not for a transformer or a pretrained backbone. If you intend to use any pretrained vision encoder, this resolution is disqualifying — you cannot recover detail that was never sampled. Budget for at least 224×224 per view, or a single wider front view plus lower-resolution peripherals.

LiDAR. Four separate problems: (1) the grid stores only max height, discarding point density — TransFuser uses a multi-channel occupancy/height grid for good reason; (2) resolution is anisotropic in the wrong direction, 0.625 m/px longitudinally against 0.3125 m/px laterally, when forward range is what you need to resolve; (3) no temporal accumulation, so a single sparse sweep is all the geometry the model ever sees; (4) the half-sweep problem in F-07.

The bigger question. Ask whether you need LiDAR at all. CarLLaVA won the 2024 CARLA Challenge camera-only. If your thesis is about lightweight edge deployment, a camera-only stack is both cheaper and easier to defend — and if you keep LiDAR, its job should be depth/occupancy in a shared BEV frame, not a fifth image-shaped input.

Is language conditioning used meaningfully, or merely appended as another vector?
Neither. It is worse than appending a vector — it is appending a hash.

Even if encode_text were replaced today with a real text encoder, the mechanism would still be weak. FiLM applies one global γ and β to every token identically. It can say "shift the whole feature space towards left-turning". It cannot say "attend to the left lane" or "watch that pedestrian" — those require the language to interact with specific spatial locations, which means cross-attention, not global modulation.

And a harder question you should sit with: does your research question need language at all? If the contribution is efficient multimodal fusion for edge autonomy, language is scope you are paying for in complexity and evaluation burden. If the contribution is instruction-following, then language is the whole point and it needs a real encoder, real instruction data, and a command-adherence metric. Right now the project is claiming the second while building neither.

Is the model actually a VLM/VLLM, or just a multimodal neural network?
It is a multimodal neural network. Call it that.

A VLM has a language model in it — a pretrained transformer over text tokens, with visual features projected into its embedding space. This has 167 K parameters total, no text tokenizer, and an 8-way categorical conditioning signal.

The accurate name is a command-conditioned multimodal driving encoder. That is not a downgrade — it is a defensible, publishable thing that is honestly described. Calling it a VLM invites the first question at your defence to be "where is the language model?", and you have no answer. Fix the name now; it costs nothing today and a great deal later.

Where should the language / vision-language reasoning component actually sit?
Outside the 20 Hz control loop, behind a typed interface — never in the gradient path of the controller.

This is the one place the existing design's instinct is right and its execution is wrong. DriveVLM-Dual's structure — a slow reasoning pathway at 1–2 Hz feeding a fast reactive controller — is the correct pattern for constrained compute, and the repo already latches a slow-pathway output. The mistake is what gets passed across that seam: a 64-dimensional opaque blob.

Make the seam a typed intent record instead:

DrivingIntent { target_waypoints : (K, 2) # ego-frame, metres lane_action : enum # follow | left | right | stop speed_cap : float # m/s hazard : bool instruction_done : bool valid_until : timestamp }

This is the deep-module move. The interface is small; everything the VLM knows sits behind it. And it buys you four concrete things: you can log what the slow pathway decided and inspect failures; you can unit-test the fast pathway against synthetic intents; you can implement the seam first with a scripted oracle driven by CARLA's route planner, so the whole fast pathway gets built and validated before any VLM exists; and you can ablate the entire slow pathway by swapping in a constant. Two real adapters — oracle and VLM — mean it is a real seam, not a hypothetical one.

What should the model output — actions, latents, waypoints, or planning tokens?
Waypoints, executed by a classical controller. Not raw steer/throttle from a monolithic network.

LMDrive, TransFuser and CarLLaVA all predict future waypoints and hand them to PID or pure-pursuit control. There are good reasons, and they apply doubly at your scale:

  • Waypoints are directly supervisable from autopilot data — you already have the collector. Raw actions are not, at least not without action-distribution mismatch.
  • Waypoints are interpretable. When the car does something stupid you can see whether perception or control was wrong. With end-to-end actions you cannot.
  • The controller enforces kinematic feasibility for free, which is what the EMA smoothing is badly approximating today.
  • A waypoint head is a much easier learning problem than a control policy, so it converges in a fraction of the samples.

Keep the latent as an internal representation, not the deliverable. And skip "planning tokens" — they buy you something only when a language model is autoregressively decoding them, which is a later phase if at all.

How should PPO interact with the multimodal model?
Not the way it does now, and possibly not at all.

Attaching PPO to a frozen randomly-initialised encoder (F-04) is the worst of both worlds — you get neither learned features nor a meaningful policy. But the deeper issue is that PPO is the wrong primary learning signal here. Single-environment CARLA at 20 FPS gives you roughly 72 K samples per hour of wall clock. PPO on a perception-heavy task typically needs millions. Every driving system in your reference folder learns by imitation.

The honest options:

  • Best: imitation learning on autopilot data for the waypoint head, then PPO as a residual correction on a small action delta, with the perception stack frozen. This is tractable and the RL contribution is well-defined.
  • Acceptable: drop PPO, do pure IL, and make the contribution about architecture and efficiency.
  • Avoid: PPO end-to-end from pixels. It will not converge in the time you have.

If PPO is non-negotiable because it is the MTP lineage, say so explicitly and scope it as finetuning. That is a defensible framing. Pretending it is the main learner is not.

The rule underneath the table: never let PPO gradients — high-variance, computed from batches of a couple of thousand correlated samples — reach a pretrained backbone. They will destroy features that took orders of magnitude more data to learn. Whatever else you do, keep the RL-trainable parameter count small and downstream.

What are the most important experiments to validate the new architecture?

Fully specified in §6. In one line: the blind baseline comes first. Train a telemetry-only policy. If it matches the full multimodal model on your metrics, nothing you build upstream will ever show up in a result, and you will have learned that for a day of compute rather than a semester.

The target shape

Four changes from the current design carry almost all of the value:

  • Replace mean-pooling with attention pooling or a waypoint head that reads tokens directly. Stop discarding the spatial representation you paid to compute.
  • Make the slow→fast interface a typed record, not a latent. Loggable, testable, ablatable, and implementable by an oracle before any model exists.
  • Output waypoints, not raw controls. Supervisable from autopilot, interpretable in failure, kinematically safe by construction.
  • Remove privileged geometry from the observation. Non-negotiable; see F-01.
Compute reality check

Direction B is only feasible if the slow pathway never runs inside the RL loop. During IL you can precompute and cache slow-pathway outputs per frame — they change at 2 Hz over a fixed dataset, so this is cheap. During closed-loop evaluation you run it live at 2 Hz. If your training hardware is a single consumer GPU, a >2 B-parameter slow pathway will not fit this budget, and the honest move is to say so and cap the model size rather than discover it in month four.

6 · Experimental roadmap

Ordered by what each experiment can invalidate. The early ones are cheap and can kill the project's premises; do them first for exactly that reason. Every experiment needs ≥3 seeds and mean ± std — the current design runs one unseeded trial.

IDExperimentWhat it decides
E0Leakage switch — an observation spec that declares exactly which fields the policy seesInfrastructure for everything below. Without it no ablation is trustworthy.
E1Blind baselines — telemetry-only vs camera-only vs camera+LiDAR, matched budgetWhether the project has a subject. If telemetry-only matches the full model, no encoder you build will ever register on the metrics. Run this before writing any new model code.

E3Route + metrics — a global route planner, plus RC / IS / DS and command adherence, and a success criterion that a parked car failsWhether any number you report means what its name says.
E4Modality ablation — RGB-only vs RGB+BEV vs BEV-only, parameter-matchedWhether LiDAR earns its place, and how the BEV should be represented.
E5Language ablation — one policy, one route set, three conditions: correct instruction / shuffled instruction / null instructionWhether "language" belongs in the title. If shuffled ≈ correct, the instruction-following claim is dead and you should reframe as Direction C.
E6Representation ablation — random-frozen vs steer/speed-pretrained vs waypoint/segmentation-pretrained vs frozen pretrained-VLM featuresWhether pretraining helps, and which pretraining task. This is LMDrive's 16.9→36.2 result, reproduced on your own stack.

Note the dependency structure: E1 and E2 can invalidate the premise of everything downstream, and both are a day or two of work each. E5 decides the framing of the thesis. E6 is the one that would actually justify a VLM. Nothing after E3 is worth running until E3 exists, because before then you have no metric that distinguishes driving from parking.

7 · What to implement first

Nothing on this list is a VLM. That is deliberate.

  1. An environment with a route and an observation spec

    One CARLA env whose step() returns a typed observation record, with a spec declaring which fields the policy may read. Privileged fields exist in info for reward and logging, and are structurally unable to reach the policy. Add a global route planner so a destination exists. This is one module with a small interface, and it is the foundation for every experiment above.

  2. Correct metrics and seeding

    Route completion, infraction score, driving score, command adherence. A success criterion a stationary car fails. random, numpy and torch seeded from SEED, and the seed recorded in every results file. Small, boring, and it makes every subsequent number mean something.

  3. E1 — the blind baselines

    Train telemetry-only, camera-only, and camera+LiDAR under the fixed protocol. Put them on one chart. Do not write any new model code until this chart exists. It is the cheapest possible test of whether the project's premise holds, and if it fails you want to know now.

  4. The DrivingIntent seam, with a scripted oracle behind it

    Define the typed record. Implement it first from the route planner and simulator state — a perfect oracle. Now the entire fast pathway can be built, trained and validated against a known-good intent stream, and the oracle's score becomes the ceiling any VLM must approach. This inverts the usual failure mode where you cannot tell whether a bad result came from the VLM or from everything downstream of it.

  5. Only then: swap the oracle for a model

    First a real frozen text encoder (Direction A). Then, if E6 justifies it and the compute budget allows, a small VLM (Direction B). By this point every piece it plugs into is already measured.

Explicitly do not do first

Repair main_vlm.py. Port anything to ONNX or TF-Lite. Tune the reward. Add pedestrians. Buy a Raspberry Pi. Add a bigger backbone. Every one of these is work that becomes obsolete or unmeasurable if E1 comes back flat.

8 · What is still unknown

Things I could not determine from the repository, and which change the recommendation above:

  • Has any of this ever run? No dataset, no checkpoint, no results directory. If it has run somewhere else, those artifacts would change the assessment materially.
  • What hardware do you have — for training, and as the edge target? Direction B is gated on this and nothing else.
  • Is PPO a fixed requirement from the MTP lineage, or is imitation learning acceptable as the primary learner?
  • Is speech a required contribution? Aanchal_Spring works but is unconnected. Whether it must be integrated changes the scope substantially.
  • Which CARLA version? This determines LiDAR semantics, whether leaderboard routes are available, and the traffic-manager API.
  • Is the deliverable a thesis with a novelty claim, or a working system? These pull in different directions on Direction A vs B.
  • What does Results_05 actually measure? The protocol behind those CSVs is undocumented beyond what the code implies.
  • The git object store in MTP_TESTING/.git is corrupt — packfile does not match index — so no history is readable and a diff-based code review could not be run. Worth repairing or re-cloning before more work lands.
